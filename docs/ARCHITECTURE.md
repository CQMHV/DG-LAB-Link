# 架构说明

DG-LAB Link 采用“入口管理交互，独立 Rust 核心持有实时链路”的结构。core、GUI、CLI、MCP 按职责分为四个可执行程序；全部客户端共用核心进程内的 ControlService 与 Hub。窗口刷新、前端热更新及 MCP 客户端重连不会成为设备输出链路的时钟源。

```text
React UI ── Tauri 命令代理 ─────────────────────────────┐
CLI ──────────────────────────────────────────────────┤
MCP 客户端 ── stdio / HTTP:17846/mcp ── dg-lab-link-mcp ┤
                                                      │ 本机 WebSocket / Bearer
                                                      ▼
                                      dg-lab-link-core:17845/control
                                                ControlService
                                                      │ 类型化 ControlCommand
                                                      ▼
                                                  Hub actor
    ├── 编译期 SourceFactory 注册表
    ├── 多设备、逐通道输入源路由与逐设备强度状态
    └── DG-LAB Socket V4 客户端
            │ WSS
            ▼
      官方 Relay ── DG-LAB 4 App ── 设备
```

## 运行边界

- Rust 后端负责官方 Relay 连接、多个 APP 与设备状态、波形节拍、逐设备逐通道路由、队列和紧急停止。
- React 前端只调用经过校验的命令，并展示低频状态快照；原始实时波形不会逐采样穿过 IPC。
- Cargo workspace 将核心库、运行时与通信库、核心启动程序、CLI、MCP 和 Tauri GUI 分开。核心启动程序生成 `dg-lab-link-core`；客户端分别生成 `dg-lab-link-cli`、`dg-lab-link-mcp`、`dg-lab-link-gui`。官方 `rmcp` SDK、stdio/HTTP 传输及 MCP 适配均位于 MCP crate，core 只提供实时链路与本机控制接口。核心、CLI 和 MCP 不依赖 Tauri、WebView 或 Node.js；Tauri 只承担窗口、托盘、自启动和本机核心客户端。
- ControlService 统一处理配置校验、Hub 更新、持久化与失败回滚；持久配置事务串行，紧急停止绕过普通配置锁。CLI 的 `call` 与 MCP 工具直接使用同一类型化命令及错误 `{code, message}`。
- 所有实时通道使用有界队列，过期数据不追赶补发。
- Socket V4 是当前主协议。旧协议只在出现真实兼容需求后独立增加。

## 共享核心生命周期

GUI、业务 CLI 和 stdio MCP 先连接已有核心，不存在时启动同目录下的 `dg-lab-link-core`。HTTP MCP 只连接已有核心，不负责启动。CLI 负责业务客户端和后台持有者，MCP 程序负责协议转发，都不承载 Hub 或实时链路。当前用户配置目录内的文件锁防止并发冷启动产生两个核心。core 仅绑定 `127.0.0.1`，本机 WebSocket `/control` 默认端口 `17845`；独立 MCP HTTP `/mcp` 默认端口 `17846`。两者使用本机随机 Bearer 令牌及 Host/Origin 检查。接口、请求、连接与响应队列都有容量限制。

`dg-lab-link-mcp` 默认提供 stdio，`--transport http` 启动本机 Streamable HTTP 服务；两种传输复用官方 Rust SDK `rmcp` 的同一工具、资源和 Schema 适配，通过本机 WebSocket 客户端转发到同一 ControlService。stdio stdout 只包含 MCP 协议消息，诊断写入 stderr，配置只包含命令路径和参数，不导出 Bearer 令牌。传输选择不改变业务能力、校验、配置持久化和停止优先级。

停止保护跨入口共享：core 接受 GUI、CLI、stdio 或 HTTP 发来的普通停止、紧急停止或 Relay 断开时，提升全局命令代次，并通过 WebSocket 通知所有客户端。HTTP 和 stdio 在协议入口接收请求时记录本地及 core 代次，在 SDK 调度、客户端排队和 WebSocket 转发过程中保留原值。core 在将可能恢复活动的命令送入共享服务前校验代次；停止前接收但尚未转发的输出、强度、触控、音频控制、同步、连接或重新配对请求会返回 `queue_busy`，不能在转发时重新取得新代次而绕过停止。因此其他 GUI、CLI 或 stdio 发起的停止同样取消 HTTP 中延迟的旧请求；客户端更新代次后明确提交的新命令可重新请求活动，Hub 和 Relay 的既有波形代次继续隔离已入队的旧输出。

每个 GUI 进程持有一次，多个设备窗口共用该持有关系；缩到托盘继续持有。前台 `serve` 或后台 CLI 是常驻持有者；一次性 CLI 和 `watch` 在连接期间持有。stdio MCP 子进程启动时自动连接或唤起核心，并在会话期间持续持有；stdin EOF、退出时释放，异常退出通过本机连接及心跳释放，其他持有者继续运行。HTTP MCP 进程以 observer 连接 core，进程和 HTTP 请求均不增加持有者；由 GUI 或 `serve` 保持核心，core 关闭时 HTTP MCP 也退出。后台 `serve` 返回 holderId，管理命令可按 ID 释放指定持有者并关闭其连接。外部 AI 客户端异常退出可能留下后台 CLI，须显式释放。

本机配置分别保存 `port`（core 控制端口）和 `mcpPort`（HTTP MCP 端口）。`mcp config --port` 持有 `mcp-http.lock` 后只更新 HTTP 端口，HTTP 服务运行时拒绝修改，core 可继续在线。旧配置只含 `port` 时将该值迁为 HTTP 端口，core 使用默认 `17845`；若旧 HTTP 端口已为 `17845`，core 使用 `17846` 避免冲突。迁移保留令牌；旧 core 仍运行时要求先退出，避免切换其控制端口。

正常退出立即释放；连接丢失或心跳失效后最长十秒内释放。最后一个持有者退出时停止接收普通请求，清理所有设备输出与强度、停止音频、断开 Relay，关闭接口并退出；清理最长等待十秒。GUI 退出释放自身持有者，其他 GUI/CLI/stdio MCP 仍持有时继续运行。核心重启只恢复持久配置，不自动连接 Relay、开始输出、恢复触点或音频活动。

## 输入源

输入源通过 `SourceFactory` 编译期注册表扩展。每个输入源负责校验自己的配置并生成统一的波形帧；协议编码只发生在 V4 边界。输入源页面可以指定本次运行中新接入设备 A/B 共用的默认来源，也可以选择“每次询问”使新设备两路保持未分配；已有设备的逐通道绑定不会被覆盖。

注册表随二进制一起构建，首版不扫描目录、不加载动态库，也不提供运行时插件安装。每台设备的 A、B 通道分别绑定一个输入源实例；同一设备和目标通道同一时刻只使用一个来源。每台设备还可独立开启 A/B 输入源同步：开启时两路立即重置为当前默认源（默认源为“每次询问”时两路均变为未分配），后续修改任一路都会同时更新两路；关闭时保留当前绑定并恢复独立选择。

## 通道输出

固定波形按设备通道持有独立游标。触控模式按设备持有触点与所有者，按通道持有波形游标。控制台的触控面板和音频控制放在对应通道内；A/B 触控面板分别给触点标注目标 `channel`，每路最多一个，两路可同时独立控制。同一设备面板共用有界输入队列与单调序列，卸载一个面板只释放它的触点，另一面板继续；未指定目标通道的 CLI/MCP 输入仍按共享路由配置分配，不可与显式通道触点混用。前端只发送归一化坐标、触点标识与目标通道，Hub 从最多 32 台设备的最新值邮箱取样，移动事件不会进入普通命令队列。窗口用单调序列与所有者标识隔离会话，按住时持续续租，失焦/隐藏/卸载发送释放；Rust 一秒租期为异常窗口提供停止保障。释放只提升目标通道的波形代次，优先发送通道清理，旧排队波形不能在清理后复活；其他通道的波形和基础强度调整保留。背景波形属于触控源内部，在释放后继续。

音频模式共用一个专用工作线程中的采集/播放时间轴，原始 PCM 不经过 Tauri IPC。有界声卡回调、文件解码与临时录音文件向分析器提供 100ms 数据块，分析器按四个 25ms 窗口计算 RMS 和 Hann 窗 FFT。音视频文件复用 Symphonia 容器解析与音频解码：优先使用默认的可解码音轨，不可解码时回退到第一条可解码音轨；视频、字幕及其他音轨的包直接跳过，只选中的音轨生成 PCM，不创建中间提取文件，也不依赖外部 FFmpeg。视频文件限制为 2 GB，压缩音频为 200 MB，选中音轨仍受一小时、采样率、声道数与音频包时长限制；WAV 使用有界 PCM 容量上限。Hub 每节拍只读取一份最新特征，再由每个设备通道独立的映射实例生成 WaveFrame；自适应阈值不跨通道共享。超过 500ms 的特征视为静默。音频 Hz 先映射为 10..100ms 输出周期，再转换为设备频率编码。官方 APP 的 WASM 数值细节尚未证实，本项目采用独立、可测试的算法，功能与配置语义对应官方模式，不承诺数值完全相同。录音在桌面端保存为 WAV。

第四种音频模式 `desktop` 通过现有 CPAL 的 WASAPI 后端，对 Windows 默认播放设备创建 input stream，启用共享模式回环（[微软说明](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording)）。使用播放设备的原生输出配置和同一有界采集管线，仅分析捕获的 PCM，不重新播放。桌面模式允许系统没有播放声音时不提供回调：500ms 后清除旧特征与表头，保留采集流；回调恢复时丢弃过期未满块。回环恢复产生的 Xrun 不视为永久故障，设备失效/配置更改则关闭采集并提示重新开启。麦克风和文件播放保持原有超时停止策略，普通/紧急停止沿用既有清理和代次隔离。

Hub 每个节拍按输入源对设备通道分组：通用状态源读取一次后扇出，固定波形按绑定取帧，触控按设备取帧，音频共用特征并按绑定映射。开始输出前，目标设备的 A、B 都必须完成分配；新接入的设备按默认来源配置，需明确开始该设备才加入输出集合。为保持队列有界，单次输出集合最多 32 台，启动时超过上限会明确报错。控制台按设备呈现仪表盘标签；主窗口切换标签只更新当前调节焦点，每个标签也可创建绑定该 `controlId` 的独立 Tauri Webview 窗口。所有窗口订阅同一个 Hub 快照，设备强度与输入源命令都显式携带目标 `controlId` 和通道，因此独立窗口不依赖主窗口当前选中项。关闭设备窗口仅销毁该 Webview；GUI 进程退出释放它的核心持有关系，最后一个持有者退出才进入全局安全清理。A、B 强度和手机端反向控制锁按设备独立维护。“同步所有设备”默认关闭；开启时，Hub 以发起操作的仪表盘设备为基准对齐全部设备的 A/B 强度。后续调整先校验所有在线设备各自的通道上限和在途操作，再根据每台设备当前值计算不同的相对增量，使其达到同一目标强度。

运行中切换某台设备的一路输入源时，Hub 只清空该设备实际发生变化的目标通道并移除该路旧波形的在途记录；若该设备已开启 A/B 源同步，则两路一起清理并切换。其他设备始终继续输出。普通停止逐台清空输出集合；紧急停止清空并归零所有在线设备。一台设备断开时其余设备继续，所有输出设备均断开后才停止输出。

## 设置生命周期

通道安全上限来自设备上报。连接超时、手机反向强度控制与触控源配置保存在本地偏好中，保存后立即生效；音频通道映射保存在当前设备会话中。重新启动不会恢复触点、麦克风、录音或音频播放。真机验收仍需确认设备上限和当前基础强度。

内置波形从固定版本的 `dglab-kit` 生成到 `shared/official-waveforms.json`，Rust 通过 `include_str!` 编译进核心，GUI 与 CLI/MCP 读取同一目录；浏览器预览也使用该提交数据。`.pulse`、JSON 与 `.pulses` 的解析和导入在核心完成，文件名和 UTF-8 文本通过业务接口传入，所有入口共用大小限制、规范化与校验。更新依赖时通过生成脚本重建目录，并由 `check:waveforms` 检查一致性；来源和许可证见 `THIRD_PARTY_NOTICES.md`。

## 配对流程

后端连接 `wss://trex.dungeon-lab.cn/v4`，从 `hello` 帧取得控制方 ID。界面据此生成 DG-LAB 4 App 可扫描的配对链接。APP 接入后，后端维护 APP、设备槽位和设备状态的快照与增量更新。

## 开发用被控端模拟器

`simulator/` 是独立的浏览器应用，通过真实 Socket V4 Relay 以被控方身份接入，不参与生产 DG-LAB Link 的运行路径。它在一个 APP 会话中维护最多 8 台虚拟 `COYOTE_030` 设备，并实现控制端当前需要的协议子集：

- `devices.get`、`devices.snapshot`、`devices.patch` 与 `slots.patch`；
- `AppendPulseData`、`AddIntensity`、`SetTempIntensity`、`SetMute` 和仅归零的 `SetIntensity`；
- 全 APP、单设备和单通道的 `device.op.clear`；
- `ping`、`custom.action` 与完整 RPC 成功/错误响应。

模拟器将每台设备和 A/B 通道的状态分别保存，可用于观察寻址是否串台、单设备断开是否影响其余设备，以及手机端反向强度变化是否按设备同步。它不模拟蓝牙时序、电气负载或真实体感。

## 安全原则

- 非零强度只通过 V4 支持的相对调整或临时强度操作完成；绝对强度操作只用于归零。
- 普通停止清理指定设备，紧急停止和最后一个持有者退出进入全局清理路径；运行中切换某台设备的输入源只清空该设备的目标通道，另一通道和其他设备继续输出。APP 断开只移除其设备，其余设备继续。
- 紧急停止优先于普通波形命令。
- 真机测试必须从低上限和低强度开始，且始终保留可立即断开的物理手段。

## 构建与发布

`build:client` 只生成 React 客户端。Tauri 的 `beforeDevCommand` 使用 `dev:desktop` 先构建调试 core、CLI 和 MCP，再启动 Vite；`beforeBuildCommand` 使用 `build:desktop` 先构建相同的生产程序，再生成前端。workspace 复用 `src-tauri/target` 输出目录，四个二进制同级；GUI、CLI 和 MCP 通过自身可执行文件目录寻找 core。当前 `bundle.active = false`，交付四个裸可执行文件；安装包、更新包和签名 bundle 不在首版产物范围内。
